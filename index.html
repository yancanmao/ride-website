01 / THE VISION

The scope is
the system.

A better local decision does not always make a better service. Routing can increase KV traffic. Scaling can be dominated by cold starts. Retaining cache can crowd out active work. A control plane must reason about demand, dependencies, state, and the cost of change together.

I.

Understand the running system

Connect programs, requests, batches, engines, KV, communication, and resources. Explain cross-layer bottlenecks, distinguish reduced demand from blocked dependencies, and make diagnosis useful to people as well as controllers.

Cross-layer diagnosis
II.

Explore better configurations

Describe components, implementations, models, policies, connections, and bindings in a common abstraction. Compare candidate configurations under constraints and use execution feedback to improve the next choice.

Configuration exploration
III.

Account for the transition

Decide whether, when, and how to change. Include model loading, state transfer or recomputation, cache rebuilding, drain, and service disruption—not only the steady-state performance of a target configuration.

Stateful online reconfiguration

02 / CONTROLLERS IN PRACTICE

Independent controllers.
Coordinated actions.

Each controller owns its policy, state, and lifecycle, with RIDE as the common management layer. These three examples are the current engineering focus, not the limit of the research scope.

01

Request Throttling

Existing integration

Which requests should run now, and which should wait?

Queue requests, control concurrency, and keep multi-turn programs associated with their model instance. Account for tool waits and program completion instead of treating every turn as an unrelated request.

02

KV Management

CPU-validated prototype

Is reusable prefix state where the next turn will execute?

Observe contiguous prefix coverage per replica, copy existing CPU KV chunks through native LMCache interfaces, and check both source and destination coverage. Track actions independently; a routing change is not proof that state moved.

Observe prefix→Copy & verify→Continue request
Design & boundaries ↗Native LMCache backend ↗
CONTROL TARGET

Cross-instance CPU KV prefixes

COORDINATION

Support request placement and continuation; unresolved copies block completion of scale-down drain.

Implementation & verification

Plugin and native registry backend validated as cloud CPU processes. Physical transfer, device bytes, and output inheritance are not yet accepted. Arbitrary device offload, GDN, and MTP state transfer are outside this version.

03

Instance Autoscaling

CPU-validated prototype

When is another model replica needed, and when can one stop?

Use target concurrency and separate scale-up/down delays to manage an approved model pool through RIDE. Route only after readiness; on scale-down, drain programs, check KV operations, then stop the exact recorded job.

CONTROL TARGET

Model processes & Ray reservations

COORDINATION

Program completion and KV state constrain scale-down together.

Implementation & verification

CPU cooperation and failure paths checked; actual model scaling and benefit remain unvalidated. Stopping a model job does not reduce the NPU allocation of its Coder/RayCluster. Platform allocation savings are not claimed.

This is the prototype's coordination sequence. General cross-controller arbitration and arbitrary policy composition remain future work.

03 / A COMMON FOUNDATION

Own the policy.
Share the runtime.

Controllers are independent packages. RIDE discovers adapters through a standard plugin entry point and manages configuration, process identity, status, logs, and lifecycle. The RIDE management API is outside the model request path; Ray executes processes and vLLM serves inference.

ASPIRATION ≠ ACCEPTANCE

Show what exists.
State what remains.

RIDE provides the management and plugin foundation. Cooperative controllers have CPU process validation. Real-model behavior, physical KV, model scaling, and full-batch benefit still require acceptance. A vision is not an implementation, and a healthy process is not proof of an effective policy.
