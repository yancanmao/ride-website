RIDE manages controller lifecycles. Each controller must separately establish what it observed, what it did, whether the action took effect, and whether the full workload improved.

Reviewed 2026-11-05. This is a versioned statement, not live telemetry. Six baseline controllers have cloud CPU process validation; real-model behavior, physical KV, actual model scaling, and performance have not completed acceptance.

01 / Request Throttling

The existing Request Throttling is one controller type in RIDE, not the whole control plane. The new cooperative-requests implements a separate FIFO, concurrency, and program-affinity policy; it is not claimed to be equivalent to the original algorithm.

  • Arriving requests wait in the request layer; occupancy remains until the full response completes.
  • Tool waits retain program affinity; completion requires an explicit release.
  • Business requests and forwarding wait without a request timeout; resource-window deadlines are separate.
  • Unknown inference outcomes retain occupancy and are not automatically replayed.

02 / KV Management

cooperative-kv uses native CPU KV copying from a pinned LMCache version; it does not implement a new transport. Copy actions and observed outcomes are recorded durably, with source cache retained.

  • Copy scope: existing full CPU KV chunks across instances, with observation limited to TP1 and fixed chunk geometry.
  • Native global lookup does not enumerate every replica. A read-only extension checks contiguous coverage per instance; registration coverage is not physical-byte verification.
  • Registered workers with no prefix coverage report zero; unregistered workers are a missing observation, not zero cache.
  • Verify the copy response and coverage at both ends. Unknown results are not replayed and prevent the affected replica from completing drain.

Not yet accepted: physical transfer, device bytes, post-copy output inheritance, and performance. Arbitrary device offload and GDN/MTP state transfer are not provided.

A strong baseline must retain native LMCache P2P cache retrieval; disabling it to manufacture a controller advantage is not a valid comparison.

03 / Instance Autoscaling

cooperative-autoscaling uses target concurrency and separate scale-up/down delays to call RIDE lifecycle operations within an approved model pool. This is an interpretable engineering starting point, not a claimed new algorithm.

  • Include a new model in routing only after actual readiness.
  • On scale-down, reject new programs, wait for existing programs to finish and release, then resolve KV operations.
  • Stop must match the exact observed job ID; refuse execution if RIDE lacks conditional_stop support.
  • Persist intent before external effects, do not replay unknown outcomes, and do not stop jobs without ownership evidence.

Model replica scaling is not platform workspace scaling. Stopping a model job frees model memory and Ray reservations, but does not automatically reduce its Coder/RayCluster NPU allocation. Reduced platform allocation cost is not claimed.

Three additional baseline capabilities

Six policy plugin types passed 68 checks on local and Linux, plus the standard RIDE six-process cloud CPU lifecycle. Earlier three-policy evidence is retained. Distributed Ray and hardware acceptance remain incomplete.

  • Routing — Called by the actual new-request entry; returns candidate order and job identities. Only the request controller reserves slots and forwards; continuations keep affinity.
  • Placement — Called by scaling to select a deployment profile already bound to a Ray node resource; the selected spec is actually submitted. This is not live free-device discovery or a resource reservation.
  • Configuration selection — Compare approved configurations using complete-batch measurements with common input/environment provenance, filter errors and quality failures, and persist a recommendation. The first version does not apply it automatically.
